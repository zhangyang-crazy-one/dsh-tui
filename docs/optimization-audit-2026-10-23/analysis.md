**dsh-tui 优化审查 · 2026-10-23**

审查基线：`1d25152831ede97cd2f706967020dd23f1053f1d`，`0.1.0-alpha.54`，Node `v22.23.1`。本轮仅分析、离线测量与记录，不修改产品代码、配置或 OpenSpec 任务状态。保留工作区原有未跟踪文件。优先级表示建议处理顺序，不表示已完成实现。

结论：优先处理终端输出正确性与 CI 的实际执行链，其次缩小生成期间的重绘范围、降低长草稿和长历史的计算量，最后收紧缓存生命周期与慢输出策略。现有行缓存、需求驱动调度和历史投影缓存应保留，不建议为这些问题重写整个渲染器。

**已验证：输出控制序列存在分块边界缺陷，建议第一优先级。**

- `tui-render/src/theme.ts:76` 与 `tui-render/tests/frame-fill.spec.ts:33` 明确使用背景色 RGB `(21,22,24)`，对应 `ESC[48;2;21;22;24m`。用户截图中的 `1;22;24m` 与其尾部一致。在这个序列中，22、24 是颜色分量；此前把它们解释为独立 SGR 样式参数并不适用于这个更具体的候选来源。
- `tui-render/src/frame-fill.ts:469` 的 `transformFrameChunk` 对每个字符串块分别加背景色前缀和 `ESC[49m` 后缀；`frame-fill.ts:544` 的写入包装没有保存未完成的 CSI/OSC 状态。
- 对同一背景色序列做 xterm headless 实验：完整序列经过包装显示 `OK`；拆成 `ESC[48;2;2` 与 `1;22;24mOK` 后直接交给终端仍显示 `OK`；两个块分别经过包装后显示 **`1;22;24mOK`**。见 `probes.json` 和 `probes.mjs`。不是“终端不能接收分块”，而是包装器在未完成的控制序列中插入了新控制码。
- 这是合成输入下已复现的组件边界缺陷。生产 Ink 正常帧往往整块输出，尚未证明真实运行中哪个调用者把该控制序列拆开，也未证明用户现场就是该路径。

建议：先记录输出调用来源、块边界、同步帧状态与光标位置，建立可重放证据；随后用有状态的控制序列处理或明确的完整帧写入契约解决边界问题。检查 Ink、布局覆盖、输入光标、鼠标选区和通知的输出协调。不要用删除数字串或定时强制全屏刷新掩盖问题。

验收：在 CSI/OSC/UTF-8 边界处分割同一输出流，完整流与分块流的终端结果一致；加入 Buffer 和字符串交替写入；持续生成、不按键、自动续跑、通知与缩放组合下，输入文本、空白单元、光标和背景均正确。诊断记录应限容量，原始会话文本仅在显式启用时保存。

**已验证：CI 的 TUI 测试路径与工作目录不一致，发布缺少构建来源核对，建议第一优先级。**

- `.github/workflows/ci.yml:40` 在默认的本仓库工作目录中启动上游 Vitest 二进制，但过滤路径是 `packages/tui/tui/tests` 和 `packages/tui/tui-render/tests`。本地按相同目录关系执行，得到 `No test files found`，退出码 1；使用绝对二进制路径不会自动切换工作目录。
- CI 只执行 `dev:setup`；`scripts/dev-setup.js:1` 明确依赖此前已运行 build 完成源文件挂载，但 CI 没有这个步骤。仅修 cwd 还不能保证测的是本仓库版本。
- `.github/workflows/publish.yml:67` 只运行根目录 `npm test` 与 pack dry-run，没有重建 bundle、运行完整 TUI 测试或核对 dist 与当前源码的关系。gitHead 一致只能说明发布记录的提交一致，不能独立证明 bundle 内容是该源码构建所得。此次没有验证当前已发布 bundle 陈旧，不能据此宣称已发生错误发布。

建议：建立一个共享的可复现验证入口，按顺序准备锁定的 DSH 工作区、挂载当前源码、生成依赖声明、typecheck、构建、运行 TUI 测试与打包导入检查；CI 和发布共同使用。发布使用已验证产物或重建后比对，记录源码与 bundle 哈希。构建挂载应使用隔离工作区，避免 `scripts/build.js:32` 的删除/复制操作覆盖日常开发中的上游改动。

验收：全新 checkout 能完成上述流程；改坏当前仓库中的 TUI 源码或测试会使 CI 失败；收集测试数不得为零；打包后的入口可导入；发布产物能追溯到实际验证过的源码。未执行远端 GitHub Actions，本项 CI 结论来自本地复现与工作流静态检查。

**已验证：生成动画与全局缓存失效扩大了刷新范围，建议第二优先级。**

- `tui-render/src/loop.tsx:2207` 每 100 ms 调用顶层 `setGeneratingTick`，所以即使没有新的模型 delta，只要状态仍是 generating，整个 `TuiLoop` 仍按约 10 Hz 更新。
- `loop.tsx:3343` 在该组件内创建 `StreamView`，后者没有整体 memo 边界；内部已有 useMemo 可以减少部分工作，但不能把父组件刷新等同于只刷新底部动画。
- `tui/src/index.ts:8146` 的通用 `emit()` 失效约二十多种 model、面板与 HUD 快照；`TuiLoop` 对这些快照使用多个 `useSyncExternalStore` 订阅。原有设置移动已经有精细通知优化，应延续该模式，避免无差别失效。

建议：先把 spinner 的计时器放入独立的小组件；再按模型、输入、设置和 HUD 的真实依赖分别失效与通知。保持未变化快照的对象身份。不要先引入新的全局状态框架。

验收：model 与历史不变时，只有动画组件发生周期更新；历史投影、输入 tokenization 和无关面板 getter 的工作量不随 spinner tick 增长；真实 model 更新、面板切换与权限弹窗仍立即生效。本轮未做改动前后的 CPU 对比，收益幅度未验证。

**已验证：长草稿和多行输入未做到按可见区域计算，建议第二优先级。**

- `composer-cursor.ts:51` 为了显示末尾的有限列，仍测量前缀并从头遍历字素；`input-bar.tsx:174` 为所有行计算窗口，`input-bar.tsx:244` 创建所有输入行。
- 每行的 `lines.slice(0, lineIndex).reduce(...)` 重算前面所有行长度，形成随行数二次增长的累计偏移工作。
- `loop.tsx:2991` 的普通文本粘贴直接进入草稿，没有长文本可见窗口限制。全量保存正文是正确的，但不必全量构建显示节点。
- 合成 SSR，三次样本中位数：700 UTF-16 单元约 11.9 ms，7,000 单元约 51.9 ms，70,000 单元约 388.7 ms。1,000 行输入生成 1,001 行渲染输出，单次约 141.0 ms。SSR 包括挂载成本，不能等同于真实按键延迟；这些数据用于证明确实存在随输入长度增长的工作。

建议：保留完整草稿，只绘制光标附近有限行；每次文本变化线性计算一次行偏移，复用字素边界与显示列索引；光标移动时更新可见窗口。大粘贴可采用折叠预览，但发送内容必须逐字不变，不应截断用户输入。

验收：相同宽度下不同长度的草稿，可见渲染节点保持有界；中文、组合字符、emoji、Tab、选区、上下移动和输入法光标正确；粘贴与发送内容一致。真实输入到 PTY 输出延迟需要另测。

**已验证：长历史的首次投影仍重，活跃回合仍复制和扫描历史，建议第二优先级。**

- 重新执行现有基准，200 / 1,000 / 2,000 条简短 user 记录的首次 `StreamView` SSR 约为 240 / 700 / 1,106 ms。这是本机单轮合成数据，不是与昨天结果的可靠提速对比，也不是 CLI 启动总耗时。
- `stream-view.tsx:1491` 对 settled transcript 逐条计算签名；此前缓存改进避免了每次重新解析所有内容，但首次仍需遍历与投影。
- `stream-view.tsx:1896` 每次合并活跃回合时复制多份 settled Map；`stream-view.tsx:1960` 的 effect 再遍历全部 `storeBlocks`，并计算包含 `JSON.stringify(meta)` 的签名后才跳过未变项。因此“历史 Markdown 不重新解析”不等于“每个 delta 与历史长度无关”。
- `stream-view.tsx:1918` 的队列在 `entryRows` 已算好后才 flush 旧快照、保留最新快照；这能减少展示帧，不能撤销已经做过的投影和扫描。

建议：先把 settled 数据与 active 覆盖层分开，按 dirty block 更新物理行存储；把可合并的展示快照调度前移，保持 canonical 会话事件完整。首次加载优先处理可见尾部，历史布局逐步计算，或缓存已知宽度的精确高度；必须保留滚动锚点，不能靠随意估高换取假流畅。

验收：固定活跃增量与 viewport，历史从 100 增长到 10,000 条时，单次 delta 的历史复制与签名计算计数不线性增长；滚动、摘要展开、宽度变化仍与完整投影一致。

**已验证：存在多层强引用缓存；总堆内存收益未验证，建议第三优先级。**

- `TranscriptRenderStoreImpl.enforceBudget` 在 `transcript-line-store.ts:616` 能驱逐物理行存储，这是已有能力。
- 但 `stream-view.tsx:1266` 的 settled 投影还持有 Markdown 行与描述符，`stream-view.tsx:1965` 的 `rebuildBlocks`、revision owner 和 signature Map 持有 block 数据；`projectorStateFor` 在 `stream-view.tsx:909` 按 block/scope 和 source 建立索引。行存储驱逐不自动释放其他引用。
- 在本文件中未发现这些长期 Map 对离开历史的 block 或旧宽度 scope 的对应删除路径。因此当前 `cacheBytes` 只描述特定行存储，不能作为整个渲染器有界内存的证明。尚未通过 heap snapshot 证明实际泄漏规模。

建议：明确每层缓存的 owner、scope 与回收时机，优先删除已不属于会话历史的 block 和过期宽度 scope；保留当前 viewport/active 必需数据。统计各层数量与字节估算，并用堆快照核查 retained size。

验收：在同一组件生命周期中重复切换会话、压缩历史与改变宽度，过期 owner/scope 数量可回落；GC 后派生缓存内存保持在声明预算附近。canonical 历史本身的存储增长要单独报告。

**已验证：现有画面验收对正文更强，对输入区与慢输出的覆盖仍可补足，建议与第一优先级同步。**

- 现有 `docs/performance-audit-2026-10-21/check-frames.mjs` 比较 transcript 快照，并用一组文本关键字检测正文越界；任意控制码残片不一定命中这些关键字。它也不完整验证输入框的空白单元和光标。
- 此次额外编写输入区 oracle，在 80×24 的无输入生成场景中检查全部 656 个同步结束帧：656 帧输入区内容正确、光标正确；655 帧有正文快照比较，正文 mismatch 为 0。未复现用户现场。
- 该 fixture 使用合成服务，约十余秒，未覆盖真实模型、长时间自动续跑和终端宿主链路。不能用其通过宣称原问题已解决。
- 输出包装器会传递底层 write 返回值，但自身没有基于 `writableLength`/drain 的待写完整帧合并策略。现有 presentation queue 的背压指标不等于已经限制 OS 输出缓冲，慢终端场景需要单独验证；本轮没有证据证明真实设备已经发生积压。

建议：把正文、输入、HUD、光标与背景纳入独立终端 oracle，增加控制序列分块与慢 sink 用例；运行分钟级生成/续跑和通知组合。确认底层写队列有界后再定帧率，不应盲目提高 FPS。若需要合帧，只合并尚未写出的完整帧，不能丢弃已经输出一半的控制序列或 canonical 事件。
