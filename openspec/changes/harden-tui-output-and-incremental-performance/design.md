## Context

基线与证据见 [审查报告](../../../docs/optimization-audit-2026-10-23/analysis.md)。已验证：跨块背景色包装可产生 `1;22;24m`、CI 路径复现失败、顶层生成计时更新、历史 Map 复制与长输入全量计算。未验证：用户现场的实际写入来源、真实终端长时间表现、堆内存泄漏规模、任何优化后的收益。阻塞：无；现场取证不阻塞已复现边界的修复。

现有边界保持：Ink 管理 chrome 与布局，物理快照管理 transcript，canonical 会话事件归 runtime，launcher 只安装与启动 plugin。历史 change 的单一正文绘制 owner、滚动延迟、工具展开上限和 overscan 合同继续有效。

基线检查为 4 个 TS 项目、46 项根目录测试、174 文件/2,335 项 TUI 测试通过。656 个合成 PTY 完成帧的输入/光标检查通过，其中 655 帧正文可比较。该结果不证明分钟级现场问题已解决。70,000 UTF-16 单元草稿 SSR 中位数约 389 ms，2,000 条简短历史首次 SSR 约 1.1 s；均不等于真实按键或启动延迟。

## Goals / Non-Goals

**Goals:**

- 输出正确性不依赖 write 块边界；诊断可定位调用来源，测试覆盖输入区与空白单元。
- 验证当前源码，发布可追溯产物；保持可重复的隔离构建。
- 对不变数据保持稳定引用，缩小动画、输入和流式增量的工作范围。
- 用操作计数、可见节点数和独立终端回放验收；时延和堆测量补充而不替代正确性。

**Non-Goals:**

- 不整体重写 Ink/React 渲染器，不引入新的全局状态框架，不重新设计 UI。
- 不修改 canonical 事件或截断用户草稿，不改变认证、模型或兼容版本策略。
- 不把合成复现当作现场结案，不把规划完成当作实现验收；本 change 不授权发布。

## Decisions

### 1. 在实际输出边界维护序列状态

保留现有组件边界，优先在输出包装层维护跨块 CSI/OSC 与字节解码状态，防止装饰前后缀插入未完成序列。与其仅要求所有上游“一次写完”，边界处理能覆盖不同来源及 Buffer 写入；完整帧 API 仍用于内部 overlay 事务，降低状态复杂度。

在实现前枚举 Ink、frame snapshot、caret、selection、notify 的实际写入路径，标注哪条经过哪些包装器。一个逻辑输出事务必须保持终端控制序列完整与顺序；完成后恢复当前输入光标。不得把“JS 回调串行”当作所有包装层与底层流自然一致的证明。

对于不完整或畸形控制序列，规定有界 pending 状态、终止与 dispose 策略并测试。必要时使用不插入装饰的连续透传策略保持解析器状态，避免无限缓存；禁止直接输出被切掉前缀的尾部作为普通文本。上限和具体状态转移在第一阶段按真实调用审查定案，并作为命名常量与测试契约，不增加用户配置项。

诊断默认只记录来源、时间、块长度、序列/同步帧状态、尺寸与光标，采用固定容量环；原始内容捕获显式启用。保存运行 bundle 身份，区分源码与现场版本。

### 2. 独立 oracle 与慢输出恢复

将 fixture 的预期草稿、布局和 canonical 内容与终端输出分开记录；以 xterm 回放检查正文、输入、HUD、空白格、颜色和光标。不得只搜索固定乱码片段或用终端实际输出生成期望值。对声明不可比较的过渡帧单独计数，不能计为通过。

慢 sink 测试控制 write(false)、drain、错误和解除阻塞。应用侧只保留有界的未开始完整展示帧，合并过时快照；已开始的事务、通知和生命周期控制必须完整、有序结束。canonical 事件不丢弃。先证明积压与恢复行为，再调整调度，不通过提高 FPS 处理问题。

### 3. 验证与发布共享同一来源链

提取源码挂载为明确步骤，在工具拥有的隔离目录准备锁定 DSH 版本及依赖，之后生成声明、typecheck、构建、完整离线测试、pack 与打包导入检查。仅使用正确 cwd 的测试执行还不够，必须核对挂载来源。根目录测试和完整 TUI 测试分别记录数量。

CI 和发布调用同一验证入口或消费同一已验证 artifact。记录提交/源码哈希、DSH 版本与锁文件身份、Node/构建工具身份及 bundle 哈希；不再按 pnpm store 中“最新 esbuild”隐式决定构建工具。验证失败、零测试、产物与源码/证明不匹配时阻止发布。保持现有 OIDC 与操作者授权边界。

选择隔离工作目录而非覆盖日常上游 checkout，避免现有 build 的 rm/cp 触及用户开发内容。既有本地编辑依赖链接继续可用，但不是发布证明。

### 4. 局部更新与输入索引

先把生成 spinner 计时移入小组件；再按模型、输入、设置、HUD 等真实依赖精确失效。保留单一 runtime 状态来源，用稳定 snapshot 与已有订阅机制实施，避免更换状态框架。涉及多个域的 mutation 必须先一致更新再通知。

草稿仍是完整权威字符串。输入区只渲染包含光标的有限行窗口；按文本 revision 构建行起点和字素列索引，移动光标复用索引。初次摄入大文本允许线性建索引；禁止每一可见行重复扫描全部前缀。窗口上限来自终端几何，显示隐藏行提示但不替换发送内容。保留选区、历史恢复、外部编辑器、IME 与图片 token 的既有语义。

### 5. 历史与活动回合分层

保留 settled 投影缓存，将 active 数据作为覆盖层读取；从变化块标识驱动物理行更新，避免每个 delta 复制所有 settled Map 或逐条 JSON.stringify 元信息。把展示请求的合并放到昂贵投影之前，canonical 事件摄入保持完整。

首次加载先形成精确可见尾部与可交互 shell，再分批建立其余索引，或复用同宽度精确布局缓存。任何后台计算都必须通过会话/宽度 revision 判旧；滚动到未准备区域应准确完成所需投影，不展示错误内容。不得以随意估高引发滚动跳动。全量同步投影保留为测试参考 oracle。

### 6. 派生缓存与生命周期

为行缓存、投影、rebuild descriptor、revision owner、signature 和 projector scope/source 索引明确 owner、有效集合、pin 与淘汰事件。历史压缩、切换会话和宽度变更后回收失效派生数据；保留 canonical 源和恢复所需的最小有效索引。

分别统计 canonical 大小、有效元数据、可驱逐行/投影、pinned 数据和待写帧。缓存预算无法容纳必要 pinned 数据时明确报告超额，不能用局部 `cacheBytes` 冒充全堆预算。先以引用数量测试证明旧 owner/scope 可回收，再用受控 GC/heap snapshot 验证 retained heap；当前没有证据支持先按“已确认泄漏”重构。

## Risks / Trade-offs

- [序列状态机过度缓存或吞字符] → 每个控制码分割点、UTF-8 字节、Buffer/字符串混合、超长未终止序列、dispose 都要有用例；定义 pending 上限。
- [精细失效漏通知] → 建立 mutation→snapshot 依赖表，使用跨域动作回归，不只看渲染次数。
- [输入窗口破坏光标/选区] → 用完整草稿作为外部真值，回放宽字符、换行、选择和 IME 位置。
- [懒投影导致跳屏] → 保留锚点与精确高度语义，按会话/尺寸 revision 丢弃过时任务。
- [按层缓存计量漏强引用] → 引用清理测试与 heap snapshot 双重验证；canonical 历史单独计量。
- [慢 sink 合帧破坏增量基线] → 未发送帧可替换；发送基线必须只随实际成功的事务更新，失败后显式失效重建。
- [基准受机器负载影响] → 固定 fixture、尺寸、Node/源码身份，先操作计数，再独立重复测量；不沿用单次 SSR 数字作为硬件时延门槛。

## Migration Plan

1. 输出复现、oracle 与验证来源链先落地，维持既有 UI 行为。
2. 分别交付动画隔离、域失效与输入窗口，独立测量并可独立回退。
3. 再交付 active/settled 增量与首屏分批，保留全量参考实现用于测试。
4. 最后收紧多层缓存和慢 sink 策略，运行长时间组合场景。
5. 每阶段运行相关回归，最终运行全部离线门禁并核对打包产物；发布仍需单独授权。失败时回退对应阶段的实现，保留可用复现测试和证据，不改变持久会话格式。

验收矩阵至少包含：80×24 与 120×40；单行 700/7,000/70,000 UTF-16 单元和 10/100/1,000 行草稿；100/1,000/10,000 条历史；至少 5 分钟无按键生成和多轮续跑；通知、缩放、选区与延迟 sink。状态以已验证/未验证/阻塞记录，逐项标记 PASS/FAIL 及证据。

## Open Questions

- 用户现场哪个写入入口/终端宿主破坏了背景序列？保留未验证状态，组件边界修复先推进。
- pending 控制序列上限、慢 sink 待写字节预算和必要 pin 预算是多少？第一阶段记录代表性最大值，选定明确上限并加入测试后再实现对应策略。
- 首屏采用分批精确投影还是复用高度缓存，哪一种能减少首次可交互时间且不破坏锚点？第三阶段用同一 fixture 比较后选择最小实现。
- 真实设备时延和 retained heap 改善幅度是多少？必须完成同环境前后测量，不能从操作量直接推算。

## Implemented parameter decisions

- 跨块控制序列 pending 上限 64 KiB；超过时连续透传直到结束，不在控制串内装饰。dispose 取消已透传未结束串并结束同步帧。
- 延迟侧通道控制最多 64 条 / 64 KiB；必须保序的应用待写队列最多 256 次 / 4 MiB。超过预算显式失败并失效绘制基线，不静默丢弃 Ink 增量；这不包含当前已开始帧、Writable内部缓存或canonical数据。
- 未开始绝对overlay按key保存最新闭包，最多16个key（当前只有正文与rail）；在drain后计算差分。诊断环128条，默认没有原始内容。
- composer窗口高度来自可用终端高度约三分之一；对不变文本复用行/字素索引，只有可见行需要tokenize。
- 历史采用精确尾部首屏与分批prepend，不引入估算高度。缓存和pins的分层预算/引用证据见 `evidence/history/`；输出调用链和队列策略见 `evidence/output/README.md`。
- 验证工作区编译DSH原生模块，要求所用Node安装含Node-API headers；本机使用已有Node24.13.0完整安装，未修改系统Node。所有bundle显式使用隔离工作区tsconfig路径，避免solution-style tsconfig落回不存在的旧lib。

- 当前render policy的每层可驱逐行缓存默认65,536行/32MiB，transcript store独立使用该policy；小预算4,096行/4MiB用于压力验证，不冒充生产默认。必要visible/overscan/active/anchor pins可超过派生缓存预算并显式报告。受控1,000条样本pins为8块/22行/600bytes，owner替换后降为2块/2行/40bytes；不对canonical源或整个V8堆承诺该上限。
